## 1. Назначение документа

Документ описывает целевую структуру базы данных интернет-магазина **AK KAGAZ**. Он предназначен для разработки PostgreSQL-схемы с использованием **Neon PostgreSQL**, **Prisma ORM**, **NestJS** и **TypeScript**.

Это спецификация для проектирования и последующей реализации. Она не означает, что все перечисленные таблицы уже созданы или что миграции разрешено применять к рабочей базе.

| Основная валюта | KGS (сом) |

### Основные принципы
1. PostgreSQL — единственный источник истины для структурированных данных.
2. **Денежные значения хранить в `Decimal(10,2)`, НИКОГДА не использовать `Float` или `Double`.**
3. Пароли хранить только в виде стойких хешей; никогда не хранить исходный пароль.
4. Секреты API, OAuth client secret и токены не хранить в таблицах каталога или настроек.
5. Права доступа проверять на backend, а не только скрывать элементы интерфейса.
6. Заказы и финансовые операции сохранять как исторические записи; не пересчитывать прошлые заказы по текущим ценам.
7. Для критичных операций использовать транзакции и идемпотентность.
8. Важные записи архивировать или помечать неактивными вместо физического удаления.
9. Схема должна поддерживать расширение, но не должна содержать сущности «на будущее» без обоснованной необходимости.

## 4. Логические домены и сущности

### 4.1 Пользователи и профиль

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `User` | Учётная запись | `id`, `email?`, `phone?`, `passwordHash?`, `status`, `emailVerifiedAt?`, `createdAt`, `updatedAt` |
| `UserProfile` | Дополнительные данные пользователя | `userId`, `firstName?`, `lastName?`, `preferredLocale` |
| `UserAddress` | Адреса доставки | `id`, `userId`, `label?`, `recipientName`, `phone`, `country`, `region`, `city`, `street`, `details?`, `isDefault` |
| `OAuthAccount` | Привязанные внешние аккаунты | `id`, `userId`, `provider`, `providerAccountId` |
| `Session` | Серверные сессии, если выбран session-based auth | `id`, `userId`, `expiresAt` |
| `PasswordResetToken` | Одноразовый токен сброса пароля | `id`, `userId`, `tokenHash`, `expiresAt`, `usedAt?` |
| `EmailVerificationToken` | Подтверждение email | `id`, `userId`, `tokenHash`, `expiresAt`, `usedAt?` |

**Правила:** email и телефон должны быть уникальными, если они указаны. Разрешить Google OAuth без локального пароля. Сырые OAuth-токены и одноразовые токены не логировать; если токены сохраняются, хранить их защищённо и только при необходимости.

### 4.2 Роли и разрешения

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Role` | Роль пользователя | `id`, `code`, `name` |
| `Permission` | Отдельное разрешение | `id`, `code`, `description?` |
| `UserRole` | Назначение роли пользователю | `userId`, `roleId` |
| `RolePermission` | Разрешения роли | `roleId`, `permissionId` |

Начальные роли: `SUPER_ADMIN`, `ADMIN`, `MANAGER`, `WAREHOUSE`, `CUSTOMER`.

Роли и permissions должны иметь уникальные коды. Сервер обязан проверять доступ при каждом защищённом запросе. Нельзя полагаться только на роль, переданную клиентом.

### 4.3 Каталог товаров

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Category` | Категории и подкатегории | `id`, `parentId?`, `slug`, `isActive`, `sortOrder` |
| `CategoryTranslation` | Названия категорий на языках | `categoryId`, `locale`, `name`, `description?` |
| `Brand` | Бренды | `id`, `name`, `slug` |
| `Product` | Карточка товара | `id`, `categoryId`, `brandId?`, `slug`, `sku`, `status`, `isFeatured` |
| `ProductTranslation` | Название и описание товара на языках | `productId`, `locale`, `name`, `description?` |
| `ProductVariant` | Вариант товара | `id`, `productId`, `sku`, `barcode?`, `attributes` |
| `ProductImage` | Фотографии товара | `id`, `productId`, `variantId?`, `url`, `alt?`, `sortOrder` |
| `ProductAttribute` | Справочник характеристик | `id`, `code`, `name` |
| `ProductAttributeValue` | Значения характеристик товара | `id`, `productId`, `attributeId`, `value` |

Уникальность SKU должна обеспечиваться на уровне БД. Для мультиязычности использовать отдельные translation-модели либо согласованную JSON-структуру; выбрать один подход и применять последовательно. Изображения хранить во внешнем файловом хранилище, а в БД — URL и метаданные.

### 4.4 Цены

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `PriceTier` | Тип/ступень цены | `id`, `code`, `name`, `minQuantity?` |
| `ProductPrice` | Цена товара или варианта | `id`, `productId?`, `variantId?`, `priceTierId`, `amount`, `currency`, `validFrom?`, `validTo?` |
| `PriceHistory` | История изменения цены | `id`, `productPriceId`, `oldAmount`, `newAmount`, `changedBy?`, `createdAt` |

Правила выбора цены должны быть едиными для корзины, заказа и админ-панели. Если ценовые ступени не используются магазином, не создавать лишнюю сложность: оставить одну базовую цену и расширить модель позже.

### 4.5 Склад и остатки

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Warehouse` | Склад/точка хранения | `id`, `name`, `address?`, `isActive` |
| `Stock` | Текущий остаток по товару/варианту и складу | `id`, `warehouseId`, `productVariantId`, `quantity`, `reservedQuantity` |
| `StockMovement` | Журнал движения товара | `id`, `warehouseId`, `productVariantId`, `type`, `quantity`, `reason?`, `referenceType?`, `referenceId?`, `createdBy?` |
| `StockReceipt` | Документ поступления | `id`, `warehouseId`, `supplierName?`, `status`, `createdAt` |
| `StockReceiptItem` | Строка поступления | `id`, `receiptId`, `productVariantId`, `quantity`, `unitCost?` |
| `StockReservation` | Резерв под заказ | `id`, `orderId`, `stockId`, `quantity`, `status`, `expiresAt?` |
| `InventoryAdjustment` | Инвентаризационная корректировка | `id`, `warehouseId`, `status`, `reason?`, `createdBy?` |

Остаток нельзя менять произвольным обновлением из клиентского интерфейса. Изменение остатка и запись движения должны происходить в одной транзакции. Нужно определить политику резервирования, отмены заказа и возврата товара до реализации.

### 4.6 Корзина

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Cart` | Корзина пользователя или гостя | `id`, `userId?`, `guestTokenHash?`, `createdAt`, `updatedAt` |
| `CartItem` | Позиция корзины | `id`, `cartId`, `productVariantId`, `quantity` |

Корзина не является источником окончательной цены. При оформлении backend заново проверяет цену, доступность товара и минимальную сумму заказа.

### 4.7 Заказы

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Order` | Заказ покупателя | `id`, `orderNumber`, `userId?`, `status`, `currency`, `subtotal`, `deliveryCost`, `discountTotal`, `total`, `fulfillmentType`, `deliveryAddressSnapshot?`, `comment?`, `createdAt` |
| `OrderItem` | Снимок позиции заказа | `id`, `orderId`, `productVariantId?`, `productNameSnapshot`, `skuSnapshot`, `unitPrice`, `quantity`, `lineTotal` |
| `OrderStatusHistory` | История статусов | `id`, `orderId`, `fromStatus?`, `toStatus`, `changedBy?`, `comment?`, `createdAt` |

`OrderItem` должен хранить снимок названия, SKU и цены на момент покупки. Удаление или переименование товара не должно портить историю заказа. Номер заказа должен быть уникальным. Изменение статуса и запись истории выполнять атомарно.

### 4.8 Платежи

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Payment` | Платёж по заказу | `id`, `orderId`, `provider`, `status`, `amount`, `currency`, `createdAt` |
| `PaymentTransaction` | Попытка/транзакция провайдера | `id`, `paymentId`, `providerTransactionId?`, `status`, `amount`, `createdAt` |
| `PaymentWebhookEvent` | Реестр входящих webhook | `id`, `provider`, `eventId`, `payloadHash`, `processedAt?`, `status` |

Предусмотреть уникальность идентификатора события провайдера в пределах провайдера. Webhook проверять по официальному механизму подписи Phoenix. Не доверять статусу оплаты, присланному браузером. Сумму, валюту и заказ перепроверять на backend.

Точные поля и статусы Phoenix уточнить по документации провайдера до реализации интеграции.

### 4.9 Доставка и самовывоз

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `DeliveryZone` | Географическая зона доставки | `id`, `name`, `region`, `city?`, `isActive` |
| `Delivery` | Доставка конкретного заказа | `id`, `orderId`, `deliveryZoneId?`, `status`, `trackingCode?`, `cost` |
| `PickupLocation` | Точка самовывоза | `id`, `name`, `address`, `phone?`, `workingHours?`, `isActive` |

Не предполагать наличие собственного курьерского API. На первом этапе статусы доставки могут обновляться сотрудниками вручную.

### 4.10 Отзывы

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Review` | Отзыв о товаре или магазине | `id`, `userId`, `productId?`, `orderId?`, `rating`, `text`, `status`, `createdAt` |
| `ReviewImage` | Изображение отзыва | `id`, `reviewId`, `url`, `sortOrder` |

Определить, разрешён ли один отзыв на товар от одного пользователя или несколько. Подтверждение покупки должно проверяться сервером. Отзывы должны проходить модерацию согласно правилам магазина.

### 4.11 Уведомления

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `Notification` | Уведомление пользователя | `id`, `userId`, `type`, `title`, `body`, `data`, `readAt?`, `createdAt` |
| `NotificationPreference` | Настройки уведомлений | `id`, `userId`, `channel`, `type`, `enabled` |
| `PushSubscription` | Подписка Web Push | `id`, `userId`, `endpoint`, `p256dh`, `auth`, `createdAt` |

Telegram-уведомления администраторам можно отправлять через backend без хранения bot token в БД. Не хранить секретные ключи VAPID в таблицах.

### 4.12 Настройки, продвижение и аудит

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `StoreSettings` | Настройки магазина | `id`, `key`, `value`, `updatedAt` |
| `Banner` | Баннеры и промоблоки | `id`, `title`, `imageUrl`, `link?`, `isActive`, `startsAt?`, `endsAt?` |
| `Promotion` | Акции | `id`, `name`, `type`, `startsAt`, `endsAt`, `isActive` |
| `AuditLog` | Журнал важных действий | `id`, `actorUserId?`, `action`, `entityType`, `entityId`, `metadata`, `createdAt` |

В `AuditLog` не записывать пароли, токены, секреты, полные платёжные реквизиты и избыточные персональные данные.

Основные связи:

- `User` N—M `Role` через `UserRole`.
- `Role` N—M `Permission` через `RolePermission`.
- `Category` 1—N `Product`; категория может иметь родительскую категорию.
- `Product` 1—N `ProductVariant`.
- `Product` 1—N `ProductImage`.
- `ProductVariant` 1—N `Stock` в разных складах.
- `Warehouse` 1—N `Stock`.
- `User` 1—1 или 1—N `Cart` — окончательно выбрать модель активной корзины.

- `Order` 1—N `OrderStatusHistory`.

- `User` 1—N `Review`.
- `User` 1—N `Notification`.

## 6. Ограничения и индексы

Обязательные ограничения:
- уникальный email, если задан;
- уникальный телефон, если задан;
- уникальный `Product.slug`;
- уникальный SKU товара/варианта;
- уникальный `Order.orderNumber`;
- уникальные пары для `UserRole` и `RolePermission`;
- уникальный `Stock` по паре склад + вариант;
- уникальный внешний transaction/event ID в пределах провайдера, если он существует;
- положительное количество в позициях заказа и складских операциях;
- рейтинг от 1 до 5;
- суммы неотрицательные, если бизнес-правило не допускает иное.

Индексы проектировать по реальным запросам:
- товары по статусу, категории, бренду и slug;
- варианты по SKU и barcode;
- заказы по номеру, пользователю, статусу и дате;
- складские остатки по складу и варианту;
- платежи по заказу и статусу;
- уведомления по пользователю и дате;
- отзывы по товару, статусу и дате.

Не создавать индексы на каждое поле без анализа нагрузки.

## 7. Транзакции и целостность

Транзакционно выполнять:
1. Создание заказа, его позиций и истории начального статуса.
2. Резервирование товара при подтверждённом бизнес-событии.
3. Списание/освобождение резерва при оплате, отмене или завершении заказа согласно утверждённому процессу.
4. Регистрацию складского движения и изменение агрегированного остатка.
5. Обработку webhook платежа и обновление платёжного/заказного статуса.

Для повторных запросов использовать idempotency key там, где это необходимо. Не полагаться на frontend-защиту от двойного нажатия.

## 8. Резервное копирование и эксплуатация

- Использовать возможности резервного копирования и восстановления, доступные в выбранном тарифе Neon.
- Не включать секреты и полные персональные данные в логи.
- Для production использовать отдельные переменные окружения и защищённые connection strings.
- Не выполнять destructive migration без резервной копии и явного подтверждения.
- Разделить pooled connection для runtime и direct connection для миграций, если это требуется используемой версией Prisma и конфигурацией Neon.

## 9. Переменные окружения

Минимальная конфигурация БД:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Основное подключение приложения к Neon; обычно pooled connection |
| `DIRECT_URL` | Прямое подключение для миграций/административных операций, если требуется конфигурацией Prisma |

Обе переменные должны находиться только в серверном окружении. Не использовать префикс `VITE_`. Не вставлять реальные значения в документацию, Git или переписку.

## 12. Критерии приёмки

База данных готова к первому этапу реализации, если:

- Prisma Schema проходит валидацию;
- все отношения и ограничения проверены;
- нет дублирующих моделей и конфликтующих enum;
- денежные поля используют Decimal;
- история заказов и платежей сохраняется;
- права доступа можно проверять на сервере;
- секреты отсутствуют в схеме и репозитории;
- миграция просмотрена и не содержит непреднамеренных удалений;
- все открытые бизнес-вопросы отмечены и согласованы;
- миграция не применена к production без разрешения владельца.
